# Development Tracking

## Overview

This document is the granular, continuously-updated task tracker for the project.

`00-development-roadmap.md` defines the official phases and freezes them once accepted — it should change rarely. This document breaks each phase into concrete subtasks and tracks their status day to day. It is expected to change often, on every PR that completes a piece of work.

Question answered:

> What is the current status of the project, task by task?

---

# How to Use This File

- Every subtask maps to a deliverable from `00-development-roadmap.md` or to a follow-up item raised during review.
- Check a box (`[x]`) only when the corresponding work is merged, not just started.
- When a phase's subtasks are all checked, update that phase's `Status` in `00-development-roadmap.md` to ✅ Completed.
- Update this file in the same Pull Request that completes the task (see "Phase 6 — Documentation Update" in `02-development-workflow.md`). A task is not done until this file reflects it.
- If a subtask turns out to be wrong or unnecessary, strike it through and note why, instead of silently deleting it — this file is also a history of how the plan evolved.

# Phase 6 — Storage Strategy — ✅ Completed

- [x] `08-storage-strategy.md` written (engine already decided: DuckDB, see `decisions/ADR-003-local-analytics-storage.md`; this phase covers the detailed strategy on top of it — raw vs. derived data, caching, denormalization). Key calls: Facts (hands/seats/actions/boards/results/tournament_results/players/sessions) are physically stored, normalized DuckDB tables; Opportunities/Events/Metrics/Aggregations from `07-analytics-engine.md` stay query-time SQL in v1 (confirmed DuckDB has no native materialized view — `CREATE TABLE AS SELECT` refreshed by hand is the only materialization path, so it's treated as a deliberate escape hatch, not a default); only cheap/unambiguous values (position, effective stack in BBs, Hero's rake share) get denormalized into Facts, everything stat-specific stays single-sourced in the query layer; hands are reprocessed via delete-then-reinsert by natural key `(room, handId)`; a cross-database player-id contract (DuckDB `players` table, SQLite notes/tags referencing the same id by value) resolves QF-5's composition; retention/tier caps enforced as a query-time filter, not deletion, so raw Facts are never destroyed by a billing-state change

# Phase 7 — Data Model — ✅ Completed

- [x] `09-data-model.md` written — real DuckDB DDL (`players`, `hands`, `seats`, `actions`, `boards`, `results`, `hand_side_pots`, `tournament_results`, `sessions`/`session_hands`, enum types, sequences) plus SQLite app-data DDL (`import_history`, `import_unparsed_lines`, `player_notes`, `player_tags`, `hand_tags`, `saved_views`, `preferences`). # Phase 8 — API Design — ✅ Completed

- [x] `10-api-design.md` written — REST/JSON over local HTTP (`decisions/ADR-004-backend-packaging.md`), `/api/v1` prefix, loopback-only with no auth. Endpoints map onto the 10 query families from `06-query-catalog.md` (mostly GET with scalar query params; `POST /stats/query` is the one deliberate exception, for QF-1's inherently structured stat/breakdown/filter parameters) plus a new write-side command surface `06-query-catalog.md` had explicitly scoped out (imports, hand tags, player notes/tags, saved-view CRUD, live-session end, report export). Key calls: money is serialized as a string, never a JSON number, to avoid float rounding on summed figures; Player/Session Profile screens compose multiple existing endpoints client-side rather than getting bespoke bundled endpoints, matching `06-query-catalog.md`'s explicit anti-one-endpoint-per-screen intent; imports are asynchronous (202 + poll) since a bulk historical import can run far past any interactive latency tier, while report export stays synchronous (already tiered "Background-acceptable" <3s); illegal stat/game-type combinations and unresolved cross-currency aggregations both degrade to an omitted value + a `warnings` entry rather than failing the whole request. Backend port discovery for the packaged app (OS-assigned port, read from process stdout, exposed to the frontend via a Tauri command) resolved as an addition to Phase 9's already-scoped packaging work, not a new ADR. Subscription/entitlement endpoints explicitly left undesigned (`03-product-vision.md`'s own cadence/mechanism TBD), and `06-query-catalog.md`'s QF-1 Scope enum was amended in the same change to add `Session(sessionId)`, needed for QF-7's composite definition to be well-formed.
